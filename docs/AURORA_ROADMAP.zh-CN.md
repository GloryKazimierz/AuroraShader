# AuroraShader：视觉方向与持续开发路线

更新日期：2026-11-13。[English roadmap](AURORA_ROADMAP.md)。

## 我们要做成什么

AuroraShader 的长期目标是一款完整、协调、适合日常游玩的奇幻光影。
Complementary 可以作为功能完整度、画面细节、可配置性和性能分档的参考；
Aurora 的配色、效果取舍和代码实现会在本项目中逐步形成。
用户已经选定的方向是：**浓郁奇幻，鲜明天空，梦幻夜景，更强的色彩表现**。

建议用下面的视觉语言建立辨识度：

| 场景 | 画面方向 | 必须保留的清晰度 |
|---|---|---|
| 白天 | 蓝青天空、温暖阳光、鲜活植被 | 石头、木材等仍能看出本来的材质色 |
| 晨昏 | 朝向太阳的一侧呈绯红、金橙，背向一侧偏紫 | 云层与地平线的细节不被亮色吞掉 |
| 夜晚 | 靛蓝夜空、偏冷月光、温暖灯火 | 地形和轮廓仍能支持正常探索 |
| 天气变化 | 雨天降低鲜艳程度，颜色平滑过渡 | 下雨时不能仍像晴天一样明亮通透 |
| 标志性夜景 | M11 仅作用于天空的青绿／紫色极光 | 可选、可控，不持续遮住正常画面 |

M11 已加入范围受限的天空极光，但实际运行画面仍待确认。浓郁色彩应主要出现在
天空、光照和发光物上，让不同场景有情绪变化，同时保留方块本身的辨识度。

## 后续工作顺序

下面是优先级，不表示每一项都能在一个里程碑内完成。每次应交付一个能审查、
能解释、有明确视觉目标的小阶段。

1. **天空与光色身份（M7）。** 做出连续的白天、晨昏、夜晚配色，朝向太阳的
   暖色，以及保护洞穴和火把的地表光色。保留原版星星、太阳与月亮。在天空
   配色插值中明确使用 sRGB 转换，同时说明现有 LDR 场景管线的限制。
2. **场景色彩基础（M8）。** 实现线性场景合成、RGBA16F 存储和单次最终曝光／
   高光映射／编码，明确初始化背景颜色。原版烘焙颜色乘积暂时作为有文档说明的
   过渡输入；后续材质阶段还可以继续迁移输入运算。这一步不是完整物理／PBR 渲染器。
3. **几何体空气感（M9）。** 在已记录表面光照之后、已知后绘制源颜色混合之前，
   加入有界的距离／高度／天气雾。未知绘制与混合路径明确保留范围限制，确认约定后
   再补齐。这是简单雾模型，不是有阴影的体积散射。
4. **受控辉光（M10）。** 先提取明亮的线性场景像素，再按面积缩到半分辨率，
   用固定可分离核模糊，在最终显示映射前加回。这不是材质自发光，天空和手持物也能
   参与。明确记录阶段与存储成本，包括关闭效果时仍存在的开销。
5. **夜景辨识度（M11）。** 只在普通上方天空加入有界的青绿／紫色光带，使用
   世界方向、周期运动，以及夜晚／天气／环境条件。原生天体和星星路径、几何体雾
   继续独立；它不是物理极光散射或新的光源。
6. **原版云大气（M12）。** 保留云几何体、已有面明暗／天气色与 alpha，在受支持
   的原生混合前，先加入有界太阳阶段色调，再按自身深度应用 M9 雾。未知混合保留
   基线；与天体／极光的覆盖仍待运行观察。自定义云几何体、体积与云阴影继续独立规划。
7. **水基础——下一优先项。** 先建立水材质识别，在雾之前加入有界天空色反射，
   保留 alpha。下一计划阶段不包含 SSR、折射或波浪。后续材质／透射工作应遵循
   明确的合成约定与场景缓冲能力。
8. **完整性。** 探索不同维度配色、植被运动、性能档位和更广泛的兼容性。
   持续检查可读性与运动中的稳定程度。

接收平面深度修正等阴影改进仍保留在路线中，但优先由实际观察到的瑕疵驱动。
不需要先把所有阴影算法研究完，才能继续建立整体画面。

## 持续开发与 GitHub 同步

用户已经授权连续推进，不再要求每个里程碑都先取得人工验收才能开始下一项。
后续按以下循环工作：

1. 选择范围清楚的改动，写明希望画面发生什么变化。
2. 实现效果，保留有用的设置和基线／回退方式。
3. 运行相关结构检查、数值检查和可用的 GLSL 编译检查，审查完整差异。
4. 同步更新中英文原理、局限和待观察项目。
5. 将完整变更提交并推送到 GitHub 开发分支。
6. 继续下一项独立工作，把待实测现象记录下来，不把预期写成结果。

日常开发在开发分支进行。推送分支不等于合并 `main`，也不等于宣布正式发布。
历史分支、旧学习项目和现有 Minecraft junction 都要保留；项目文件继续放在 D:。

用户已通过 `/goal nonstop` 明确启用持续开发目标。后续按完整的小阶段连续推进，
让代码、验证和知识一起留下来，不再为日常里程碑验收停下，也不能因为完成一个
功能就把整个产品目标标为完成。提交与下一步记录用于跨开发轮次衔接；
实际运行证据仍单独记录。

## 知识要与代码一起留下来

每个视觉系统都应在 GitHub 中留下：

- 它解决什么问题、希望呈现什么画面、由哪个渲染阶段负责。
- 坐标空间、公式、默认值，以及各项保护条件存在的原因。
- 真正执行过的检查，与仍需 Minecraft／Iris 观察的部分。
- 可重复的对照方法；没有观察过的结果保留空白。
- 实现取舍和适合 Graphics／Rendering 面试的简洁解释。
- 下一步工作记录，区分代码开发与尚未补充的运行观察。

静态检查或独立编译器通过，不能写成 Minecraft／Iris 运行成功。
没有性能测量，也不声称速度提升。
