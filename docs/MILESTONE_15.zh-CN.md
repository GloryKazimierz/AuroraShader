# Milestone 15：本机 GPU 验证

日期：2026-11-13。分支：`codex/milestone-15-gpu-validation`。
基线：M14 提交 `e8007b21b8e0c4f13d44312b3c62959dbac1b326`。
[English version](MILESTONE_15.md)。

M15 增加 Windows 驱动验证工具，不改变着色器的画面行为。
它可以在真实 OpenGL 驱动上编译、链接项目变体，并绘制选定的合成输入，不必启动 Minecraft。
这不等于 Iris 运行测试，也不是性能基准测试。

## 1. 三种不同层次的证据

| 层次 | 能确认什么 | 不能确认什么 |
|---|---|---|
| 已有 CPU/结构检查和独立 GLSL 检查 | 数学不变量、源码约定、离线编译器接受的语法 | 当前 GPU 驱动上的实际执行 |
| M15 本机 OpenGL 检查 | 驱动编译/链接，以及明确合成输入下的实际帧缓冲结果 | Iris 补丁、Minecraft 绘制调度、原生资源/状态设置或完整游戏观感 |
| Minecraft 配合 Iris | 集成后的画面、相机运动、世界几何、资源包及游戏交互 | 仅凭一次观察就保证所有 GPU、设置和场景正确 |

这些层次互相补充。新增层次通过，不会把之前尚未观察的 Minecraft 结果自动改成通过。
同样，在 Windows 设备列表中找到一个显卡，也不能证明某次测试使用了它；
需要由实际创建的 OpenGL 上下文报告自己的身份。

## 2. 隐藏窗口承载真实 OpenGL 上下文

C++ 测试程序创建一个小型、从不显示的 Win32 窗口，拥有独立的设备上下文。
选择并设置像素格式后，先创建临时 WGL 上下文，加载现代上下文入口，
再请求 OpenGL 3.3 compatibility。

像素格式必须在创建上下文前设置，而且同一窗口只设置一次。
现代 WGL 扩展负责指定所需版本和 profile。
[Microsoft 像素格式约定](https://learn.microsoft.com/en-us/windows/win32/api/wingdi/nf-wingdi-setpixelformat)，
[WGL 上下文/profile 规范](https://registry.khronos.org/OpenGL/extensions/ARB/WGL_ARB_create_context.txt)。

项目使用 `#version 330 compatibility` 和兼容模式内置变量，因此 profile 很重要。
隐藏窗口只是上下文载体；测试像素写入显式创建的帧缓冲对象，不显示在桌面上。
程序不会显示/聚焦窗口，也不会启动游戏。

已成功执行的初始上下文探测报告：

| 字段 | 实际观察值 |
|---|---|
| 厂商 / 渲染器 | Intel / Intel(R) Iris(R) Xe Graphics |
| OpenGL | 3.3.0 - Build 31.0.101.3962 |
| GLSL | 3.30 - Build 31.0.101.3962 |
| Profile | Compatibility，mask 2 |
| 最大纹理尺寸 / 片元纹理单元 | 16384 / 32 |

这证明回答探测的是该 Intel 上下文，不代表机器上其他已安装 GPU，
也不是 Minecraft/Iris 的观察结果。
单独探测成功还不能说明着色器已经编译，或绘制像素已经与参考一致。

## 3. 两个工具分别负责什么

| 文件 | 职责 |
|---|---|
| `tools/gpu_harness.cpp` | 隐藏 WGL 上下文、驱动编译/链接、FBO 绘制/回读和结构化错误 |
| `tools/validate_gpu.py` | 用已有 C++ 编译器构建程序、准备案例、比较结果，并可选保存报告 |
| 已有验证器 / 着色器源码 | 提供源码变体和独立 CPU 参考计算 |

生成的可执行文件、展开源码、清单和像素数据使用 D 盘项目旁边的新临时目录。
编译器子进程的 `TMP`、`TEMP` 和 `TMPDIR` 也指向该新目录。
运行器不下载编译器、不安装图形库，不修改 Minecraft 配置/世界/junction，也不改变光影设置。
可选报告是明确保留的产物；清理临时目录和创建报告是两项分开的工作。

在 Windows 中，从项目根目录使用 Python 和已安装的 MinGW 编译器运行：

```powershell
python -B tools/validate_gpu.py --cxx C:\msys64\ucrt64\bin\g++.exe --suite probe
python -B tools/validate_gpu.py --cxx C:\msys64\ucrt64\bin\g++.exe --suite compile
python -B tools/validate_gpu.py --cxx C:\msys64\ucrt64\bin\g++.exe --suite render
python -B tools/validate_gpu.py --cxx C:\msys64\ucrt64\bin\g++.exe --report docs/validation/M15_GPU.json
```

默认套件为 `all`；`compile` 和 `render` 也各自先探测上下文。
省略 `--cxx` 时，运行器从 PATH 查找已安装的 `g++`。
只有明确指定时才保存报告。成功报告记录套件、驱动、规范化的着色器源码摘要、
案例比较结果及其容差。确认成功之前还会再次检查源码摘要，
运行中途着色器发生变化会使结果无效。运行器拒绝已知的软件渲染器名称，
不会把它们写成硬件 GPU 成功。失败会抛出错误；运行器仍会清理已经验证的新临时目录，
且不会创建成功报告。

已有报告路径会被拒绝，而不是覆盖。后续观察使用新报告名，保留可审查的驱动、输入和结果。
不能仅凭 JSON 文件存在就推断成功；需要检查其中的状态、阶段和结果。

## 4. 编译与链接是两种检查

运行器准备受支持的着色器设置变体，把每对顶点/片元程序交给真实驱动。
编译检查每个阶段的 GLSL；链接检查这些阶段能否组成一个可使用的程序。

这里使用项目源码与测试预处理，并不执行 Iris 的 Java 补丁器，也不会重建 Iris
供应的所有内置别名/状态。驱动链接成功是有用证据，但不能单独证明完整的游戏内兼容性。

选项矩阵来自已有 `compile_glsl.py` 生成器，避免手动维护第二份变体列表。
include 展开和选项覆盖共用原有逻辑。
其中渲染阶段常量只是编译用占位值，游戏中由 Iris 提供实际值。
该矩阵是选定的覆盖集合，并不是所有光影设置的完整笛卡尔积。

## 5. 把合成像素绘制到 FBO

帧缓冲对象（FBO）把绘制目的地连接到纹理存储。
测试程序确认附件配置完整，明确设置视口/uniform/纹理状态，绘制后回读像素。
不完整的 FBO 属于错误，不能拿黑色输出继续当成有效比较。
[OpenGL 3.3 compatibility 规范，第 4.3–4.4 节](https://registry.khronos.org/OpenGL/specs/gl/glspec33.compatibility.pdf)。

这些隔离测试关闭混合、深度/模板、抖动和自动帧缓冲 sRGB 转换，
让输入的着色器数学和存储选择更容易检查。
它们并不模拟 Minecraft 的完整透明合成或帧缓冲生命周期。

| 案例类别 | 输入约定与检查内容 |
|---|---|
| 测试程序对照 | 不对称行/通道、权重不同的双采样器和非平凡矩阵检查覆盖、方向、绑定与矩阵上传；故意无效的输入必须失败 |
| 泛光 | 实际提取、水平模糊、竖直模糊与合并程序；7x5、3x3、8x6 输入、末尾亮像素、变化 alpha、选定阈值/软拐点/强度及回退 |
| 水面法线 | 用合成 wrapper 调用实际 `waterWaveNormal`；负/大/整数极限锚点，时间循环/静态/无效时间，强度/适用范围与旋转/缩放/奇异矩阵 |
| 最终显示 | 实际 final 程序；合成线性颜色、选定高光映射/曝光、可选灰度与 alpha 保留 |

泛光源和中间存储都使用 `RGBA16F`。
每个阶段既与以前一阶段 GPU 输出为输入的 CPU 参考比较，
完整链条也与单独传播的 CPU 结果比较。
案例显式把阶段输出送入后续纹理输入，不检查 Iris 自动缓冲翻转。
隔离的 2x1 合并回退案例，并不证明 Iris 半分辨率分配支持单像素窗口。

水测试把法线分量写入 `RGBA32F`，没有绘制真实水几何体，
没有证明材质分类器的游戏集成，也不覆盖完整的 M13 反射/雾/混合路径。
最终显示测试使用可控的 `RGBA32F` 输入/输出，不测试显示器或操作系统颜色配置。

回读格式为 RGBA float32，底行在前。
被优化掉的绑定必须在对应回退案例中明确允许，意外失活的绑定会被拒绝；
故意拼错采样器名称的案例验证这项拒绝。
每个目标先清为有限的负数哨兵值。全部 discard 的对照必须保留该值，
且把这个没有写入的目标与预期零值比较时必须失败，避免漏画被误判为正确的黑色输出。
正常输入对照检查数据通路；错误 GLSL、链接接口、uniform 类型、原始图像长度和输出文件冲突
检查其他失败处理。

合成输入本身就是约定：尺寸、纹理格式、uniform、矩阵、坐标、时间与预期输出都由案例指定。
测试能暴露这些输入下的驱动/编译器或实现问题，
但不能证明真实帧中 Iris 会在同一时刻提供相同数据。

## 6. 半精度存储和比较容差

`RGBA16F` 附件用四个半精度浮点分量保存颜色。
把它回读到 32 位浮点数组，并不能恢复写入时已经丢失的精度。
多阶段泛光可能在多个中间存储边界上舍入，
因此逐位比较无限精度 CPU 运算并不是正确的测试约定。

CPU 参考在泛光存储边界上舍入到半精度。逐通道比较规则为：

```text
error = abs(gpu - expected)
allowed = absolute + relative * abs(expected) + halfUnits * halfULP(expected)
仅当两值均有限且 error <= allowed 时通过
```

`halfULP` 根据预期半精度数值的量级估算间距，最小非正规数步长为 `2^-24`。
当前案例限制为：

| 比较 | 允许误差 |
|---|---|
| 泛光每个阶段 | 2 个 half ULP + 0.000002 |
| 泛光完整链条 | 4 个 half ULP + 0.000004 |
| 泛光回退、可精确表示的测试对照 | 完全一致 |
| 启用的水面法线案例 | 绝对误差 0.00006 |
| 水面回退案例 | 完全一致 |
| 最终显示 | 0.000003 + 0.00002 * abs(expected) |

泛光和最终显示的 alpha 还会单独要求完全一致。
报告记录最大绝对误差，以及允许容差被使用的最大比例。
水面 CPU 参考模拟有关相位运算的 float32 行为，
不是直接拿无限精度理想值与硬件盲目比较。

有用的比较应区分少量预期数值差异与结构性错误，
例如尺寸错误、通道互换、alpha 损坏、纹理绑定错误或阶段顺序变化。
NaN/Infinity 不能悄悄被当成一致。
容差应对应具体案例和格式，不是视觉喜好的阈值，也不能替代对公式的检查。

回读会等待相关绘制工作完成，并把数据传回 CPU。
本工具用于正确性检查，不用于测量正常游戏帧。
构建/编译/执行总耗时不是光影 FPS，也不是有效的 GPU 性能基准。

## 7. 先定位失败，不急着改变画面功能

| 失败阶段 | 首先检查 |
|---|---|
| 编译器查找/构建 | 编译器路径、已有头文件/库和 C++ 构建输出 |
| WGL 设置/探测 | 精确 Windows 错误、可用版本/profile 和报告的渲染器 |
| 着色器编译 | 变体名、顶点/片元阶段和完整驱动日志 |
| 程序链接 | 阶段接口和链接日志 |
| FBO/纹理设置 | 尺寸、格式、附件完整性与 OpenGL 错误 |
| 像素比较 | 案例输入、逐阶段存储精度、容差和最大误差 |
| 报告创建 | 目标是否存在，以及原始成功/失败执行记录 |

把案例名称/输入约定和驱动身份一起记录。
不要遇到数值失败就盲目放宽容差，也不要把因驱动失败而跳过的测试悄悄写成通过。

## 9. 六个实用渲染问题

1. **有 GPU 测试后为什么还保留 CPU 测试？** CPU 能低成本地隔离公式和广泛参数不变量，
   GPU 检查的是另一个执行层次。
2. **GLSL 为什么可能编译成功但链接失败？** 单个阶段合法，不代表接口或组合后的程序要求兼容。
3. **为什么用 FBO 而不用截图？** 可控纹理存储和数值回读便于精确比较，避免桌面/UI 差异。
4. **为什么活动渲染器字符串重要？** 混合显卡机器可以有多个 GPU，
   只有创建出来的上下文能说明本次使用哪个实现。
5. **为什么允许数值容差？** 存储精度和浮点求值有差异，但预期运算应保持在有理由的小范围内。
6. **为什么仍不是 Iris 测试？** 游戏/模组提供的变换、补丁、绘制顺序和资源，
   并不由小型合成测试程序负责。
